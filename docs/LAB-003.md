# LAB-003 — OPERATIONAL CORE (documentação técnica essencial)

Evolução do **FIRE Agent Command Center** (LAB-001 → LAB-002 → LAB-003) para uma central
operacional preparada para o gerenciamento real de múltiplos agentes de IA, com o ChatGPT
como inteligência central de supervisão e arquitetura pronta para o **FIRE Private AI**.

Base desta entrega: branch `feature/trae-lab-003`, criada a partir do commit validado
`98b36caf242cf4b239929a3b7a008113757ec915` (LAB-002). **Nada foi reconstruído**: toda a
funcionalidade herdada (painel, agentes, projetos, Kanban, executor local, integrações,
histórico, backup, Code Lab, central de missões) foi preservada.

## Princípios de honestidade operacional

Toda a camada nova segue três regras não negociáveis:

1. **Não inventar.** Nenhuma API, endpoint, versão, token ou capacidade é fabricada. Integrações
   externas permanecem `nao_autorizado`/`indisponivel` até haver credencial e autorização
   fornecidas pelo proprietário e verificadas de fato.
2. **Não simular execução externa como real.** O único executor que roda de verdade nesta
   entrega é o **executor local determinístico** (não é IA). Execução por agente externo só
   existe como **fluxo manual assistido** (exportar missão → importar resultado).
3. **Não fabricar desempenho nem custo.** Métricas e recomendações usam apenas dados
   observados. Campos sem base retornam `null`/`[]`/"Sem dados", nunca um número plausível.
   Consumo é sempre **informado** pelo operador; nenhuma API paga é consultada.

## 1. Backend e persistência

### Camada desacoplada (`src/platform/persistence.ts`)

Uma porta (`RepositoryPort`) com três implementações:

| Implementação | Estado | Descrição |
| --- | --- | --- |
| `MemoryRepository` | ativa | Em memória; usada nos testes. |
| `LocalRepository` | ativa | `localStorage` (chave `fire-agent-command-center:ops:v1`). Comportamento atual da aplicação. |
| `SupabaseRepository` | **desativada** | Preparada, mas `disponivel = false`. Não há projeto/credencial autorizados; não inventa endpoints nem faz chamadas. |

`criarRepositorio(modo)` seleciona a implementação. Todo estado carregado passa por validação
(`parsePlatformState` / `parseOpsState`): registros inválidos são descartados, campos são
coagidos para tipos válidos e a coerência de evidências/ativos é restaurada. As **migrações são
sempre relidas do código-fonte** (fonte única de verdade), nunca de conteúdo persistido.

### Schema PostgreSQL (`backend/migrations/`)

Migrations versionadas e **espelhadas** por `src/platform/migrations.ts`. Nenhuma é aplicada
automaticamente.

| Versão | Arquivo | Conteúdo |
| --- | --- | --- |
| `0001` | `backend/migrations/0001_init.sql` | Tipos enumerados, `schema_migrations`, organizações, usuários, agentes, projetos, missões, dependências, `mission_runs`, `run_attempts`, `run_eventos`, evidências, aprovações, `audit_log`, `usage_metrics`. Inclui índices únicos de idempotência e *checks* de coerência. |
| `0002` | `backend/migrations/0002_rls.sql` | Row Level Security, isolamento entre organizações e autorização por papel via funções `app.usuario_atual()`, `app.organizacao_atual()`, `app.papel_atual()`. |
| `0003` | `backend/migrations/0003_indices_funcoes.sql` | Índices de desempenho, função de verificação de dependências e gatilhos de `atualizado_em`. |

**Guarda de segurança dupla.** Cada arquivo SQL aborta por padrão:

```sql
do $$
begin
  if coalesce(current_setting('fire.allow_migrations', true), '') <> 'authorized' then
    raise exception 'Migração bloqueada: defina fire.allow_migrations = ''authorized'' ...';
  end if;
end $$;
```

E, no código:

```ts
aplicarMigracoes(); // → { aplicadas: 0, motivo: "Aplicação de migrações bloqueada: ..." }
```

**Nenhuma migration foi aplicada em banco real.** Aplicar exige autorização específica.

### Organizações, usuários e isolamento (RBAC)

- Papéis: `proprietario`, `administrador`, `operador`, `revisor`, `observador`.
- Matriz de permissões de **menor privilégio** em `PERMISSOES_POR_PAPEL` (`src/platform/types.ts`).
- `autorizar(usuario, permissao, organizacaoIdDoRecurso)` (`src/platform/authz.ts`) é a **única**
  forma correta de liberar uma operação sensível — combina usuário ativo + permissão + organização.
  Recurso de outra organização é sempre negado, mesmo com id válido.
- A semente (`src/platform/seed.ts`) cria duas organizações de demonstração (`org-demo`,
  `org-lab`) e quatro usuários de exemplo (proprietário, operador, revisor, observador). Todos
  os e-mails usam o domínio reservado `.invalid`.

### Persistência herdada preservada

O estado demonstrativo continua em `localStorage` sob `fire-agent-command-center:state:v2`
(modelo v2, `src/types.ts`). O núcleo operacional usa uma chave separada
(`fire-agent-command-center:platform:v1` para a plataforma e `...:ops:v1` para o estado
operacional consolidado), garantindo que a camada nova não corrompa os dados existentes.

## 2. Motor de orquestração

`src/orchestration/` — funções **puras e determinísticas** (nenhuma chamada de rede).

- **`types.ts`**: `RunStatus`, `MissionRun`, `RunAttempt`, `RunEvento`, `EngineConfig`,
  `MissionView`, `QueueEntry`. Configuração padrão: concorrência 3, timeout 30 s, 3 tentativas.
- **`stateMachine.ts`**: tabela de transições validada. `executando` pode retornar a
  `enfileirada` (retentativa), o que sustenta o tratamento de falhas/timeout.
- **`engine.ts`**: o ciclo do motor (`processar`) executa quatro passos:
  1. **Timeout** — expira execuções cujo tempo ultrapassa `timeoutMs` (com retentativa controlada).
  2. **Dependências** — alterna entre `aguardando_dependencia` ⇄ `enfileirada` conforme as
     dependências são concluídas.
  3. **Concorrência / prioridade** — inicia apenas runs prontas (`enfileirada`), respeitando
     `maxConcorrencia` e a ordenação por prioridade (alta → média → baixa) com desempate por
     ordem de criação.
  4. **Aprovação humana** — operações `critica` sem aprovação são travadas em
     `aguardando_aprovacao`.
- **Idempotência**: `enfileirar` recusa criar uma segunda run não-terminal com a mesma
  `chaveIdempotencia` (por padrão `organizacaoId:missaoId`).
- **Cancelamento, retentativas, falhas e histórico**: cada transição gera um `RunEvento`; cada
  tentativa é registrada em `RunAttempt`. O histórico completo fica na própria run.
- **Missões sequenciais e paralelas**: dependências definem a ordem sequencial; o paralelismo é
  limitado por `maxConcorrencia`.

O motor **não executa** a tarefa: delega ao chamador (ver `localRunner.ts`), o que o mantém
testável e honesto.

### Executor local real (`src/orchestration/localRunner.ts`)

Único executor automático desta entrega. Processa o texto de instruções no próprio navegador e
**reconfere o resultado por caminho independente** (checksum FNV-1a), reutilizando
`src/domain/localExecutor.ts`. O resumo é explicitamente rotulado `(execução local, não IA)`.

### Aprovação para operações críticas

`src/platform/guards.ts` classifica as operações críticas (`execucao_externa`, `deploy`,
`exclusao_massa`, `alteracao_seguranca`) e exige aprovação humana. `execucao_local` é `normal`.

## 3. Adaptadores de agentes

`src/adapters/` — arquitetura extensível e **honesta**.

- **`types.ts`** define a interface `AgentAdapter`: identificação, capacidades, status de conexão,
  `validarDisponibilidade`, `enviarMissao`, `consultarExecucao`, `receberResultado`, `tratarErro`
  e `controleConsumo`.
- **`registry.ts`** (`criarRegistro` / `listarAdaptadores` / `obterAdaptador`) instancia um
  adaptador por provedor: ChatGPT, Codex, ChatGPT Work, TRAE, Manus, FIRE Private AI e agentes
  personalizados.
- **`capabilities.ts`** é o catálogo de requisitos reais de ativação. `canalOficial` é `null`
  porque **não inventamos URLs oficiais**.

Comportamento por tipo:

- **Provedores externos** retornam `nao_autorizado` (ou `indisponivel`, no caso do FIRE Private
  AI) e **recusam o envio automático**, direcionando para o fluxo manual assistido.
- **Agentes personalizados** (`custom`) são a única modalidade utilizável hoje (junto ao executor
  local): operam **exclusivamente** em fluxo manual assistido.

### Fluxo manual assistido (`src/adapters/manualFlow.ts`)

- `exportarMissao(missao, ctx)` gera o prompt completo da missão e um nome de arquivo
  (`missao-<codigo>.md`).
- `importarResultado(texto)` é **defensivo e determinístico**: extrai apenas o que está
  literalmente no texto (pares `chave: valor`, URLs, hashes hexadecimais). Não inventa resumo,
  artefato ou métrica.

## 4. Inteligência operacional

`src/intelligence/` — só mede o que foi observado.

- **`metrics.ts`** (`calcularMetricasAgente` / `calcularMetricasTodos`): missões concluídas,
  falhadas, taxa de sucesso, tempo médio, erros, testes aprovados, retrabalho, consumo informado
  e especialidades. Sem dado suficiente, os campos retornam `null`/`[]`.
  `calcularEspecialidades` deriva especialidades **apenas** de evidências
  `verificado_independente`.
- **`recommendation.ts`** (`recomendarAgentes` / `melhorRecomendacao`): pontuação 0–~100 somando
  apenas sinais observáveis (taxa de sucesso até +60; testes aprovados até +20; retrabalho
  penaliza até −20; tempo médio bonifica até +20). A **confiança** é derivada do tamanho da
  amostra (0 runs → `sem_dados`; ≥5 → `alta`). Um agente sem execuções recebe pontuação `0` e
  justificativa "Sem execuções registradas" — nunca desempenho inventado.

O proprietário pode **escolher manualmente** um agente ou usar a **recomendação automática**.

## 5. Central de evidências

`src/evidence/center.ts` + `src/platform/types.ts`.

- Tipos (`EvidenceKind`): repositório, branch, commit, pull request, deployment, teste, captura,
  relatório, arquivo, bloqueio.
- Origem (`OrigemDado`): `informado_agente`, `informado_operador`, `verificado_independente`.
- `criarEvidenceRecord` mantém a **coerência**: só `verificado_independente` pode ter
  `verificadoPor`/`verificadoEm`.
- `verificarIndependente(evidencia, verificador)` promove uma evidência a verificada — e **exige
  um verificador identificado**. Sem verificador, a operação falha.
- `separarPorOrigem` / `resumirEvidencias` separam claramente o que é informado do que é
  verificado, exibindo os contadores na interface.

## 6. Segurança e controle de custos

- **Validação de entradas** (`src/platform/validation.ts`): `sanitizarTexto`, `validarNome`,
  `validarEmail`, `validarIntervalo`, `validarMissao`.
- **Detecção de segredos**: regex para chave OpenAI (`sk-`), `Bearer`, AWS (`AKIA`), cabeçalho de
  chave privada, campos `api_key|secret|password|senha|token` e JWT. `garantirSemSegredos` lança
  antes de persistir/exportar. **Nenhum token/segredo é armazenado no frontend ou no
  `localStorage`.**
- **Bloqueio de operações externas e de gasto** (`src/platform/guards.ts`):
  `permitirOperacaoExterna` e `permitirGasto` negam por padrão; `limites.operacoesExternasPermitidas`
  e `limites.gastoPermitido` são `false` nesta entrega.
- **Limites de execução**: `verificarLimitesExecucao` (fila e execuções por missão) e
  `estimarCustoExcedido` (teto informado; nunca calcula preço real de API paga).
- **Auditoria**: toda mutação relevante em `opsReducer` gera um `AuditEntry` (ações permitidas e
  negadas). O histórico é limitado a 500 entradas.
- **Escopo respeitado**: nenhum outro projeto FIRE é acessado; o projeto Vercel da Yasmin Rocha
  não é tocado; nenhum serviço pago é contratado; nada é publicado em produção.
