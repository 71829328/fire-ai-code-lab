## 0. Princípios de honestidade operacional

1. **Não declarar integração ativa sem chamada real bem-sucedida.** Um adaptador existir
   **não** significa que o provedor está conectado. A Central de Conexões diferencia
   explicitamente os 7 estados (ver §9).
2. **Nenhuma credencial do ambiente TRAE é lida ou reutilizada.** Só variáveis próprias da
   aplicação (`FIRE_*`, `SUPABASE_*`, `GITHUB_TOKEN`, `VERCEL_TOKEN`) — mantidas
   exclusivamente server-side.
3. **Nenhuma operação sensível depende de validação frontend.** Toda autorização,
   validação de entrada, rate limiting e kill switch vivem no servidor.
4. **Não inventar APIs privadas nem automatizar interfaces sem autorização.** Agentes sem
   integração oficial permanecem em **fluxo manual assistido**.

## 1. Backend seguro (`src/server/*` + `api/*`)

Arquitetura desacoplada e compatível com o runtime serverless do Vercel:

- `src/server/*` — lógica **framework-agnóstica e testável** (`ApiRequest`/`ApiResponse`).
- `api/[...rota].ts` — adaptador **fino** (`export default criarHandler()`), traduz a
  requisição HTTP real para `ApiRequest` (incluindo `query.rota` como array de segmentos).

### 1.2 Controles server-side

- **Sessões assinadas** HMAC-SHA256 (`node:crypto`), formato `v1.<payload>.<assinatura>`,
  TTL 8h; senhas com `scrypt`.
- **RBAC** (`Papel`: proprietário, administrador, operador, revisor, observador) com
  `autorizar()` aplicado **antes** de qualquer efeito.
- **Isolamento por organização** em todas as leituras/escritas.
- **Rate limiting** em memória (janela deslizante), chave `ip::rota`.
- **Validação de entrada** centralizada (`esquema.ts`) — corpo inválido → `400`.
- **Tratamento de erros** uniforme (`http.ts`): códigos estáveis, sem vazar stack/segredos.
- **Kill switch** (`preferencias.ts`): provedor desativado é bloqueado **antes** de qualquer
  chamada de rede (`503`) e nunca aparece como conectado.

## 2. Supabase e autenticação

- Adaptador Supabase (`src/server/supabase.ts`) completado; permanece **não configurado**
  quando faltam credenciais (não inventa endpoints, não faz chamadas).
- Autenticação real suportada por **e-mail/senha**; **Google OAuth** e **Microsoft OAuth**
  preparados, expostos apenas quando `capacidadeOAuth()` detecta configuração presente.

### 2.1 CORREÇÃO OBRIGATÓRIA (CTO) — removida a falsificação de identidade

A versão da LAB-003 aceitava `current_setting('app.usuario_id', true)` como identidade
**alternativa** em `app.usuario_atual()`. Isso permitia **falsificação de identidade** e
escalada de privilégio por qualquer sessão capaz de ajustar esse parâmetro.

**Corrigido em `backend/migrations/0002_rls.sql`:** a identidade agora vem exclusivamente de
`auth.uid()` (resolve o `sub` do JWT verificado — não controlável pelo usuário). Identidades
de teste existem **somente** em `backend/migrations/local/0000_auth_stub_local.sql`, que
**nunca** é aplicado em banco real/homologação/produção.

```sql
create or replace function app.usuario_atual() returns uuid
language sql stable as $$
  select auth.uid();
$$;
```

### 2.2 Auditoria de segurança das migrations

- **SECURITY DEFINER**: usado apenas em funções de leitura de identidade, todas com
  `set search_path = public, pg_temp` (bloqueia sequestro de search path).
- **Grants**: mínimo necessário; `0004_seguranca.sql` endurece permissões e revoga `public`.
- **Escalada de privilégio**: troca de papel sensível exige papel adequado; alterações
  indevidas são bloqueadas por gatilho.
- **Isolamento entre organizações / integridade entre tenants**: políticas RLS em toda
  referência cruzada.
- **Imutabilidade da auditoria**: `UPDATE`/`DELETE` em `run_eventos`/`audit_log` bloqueados.
- **Aprovação de operações críticas**: fluxo explícito; revisor altera decisão sob regra.

Migrations/RLS executadas **somente** em **cluster PostgreSQL efêmero local** via
`backend/scripts/rls-local.sh` (initdb + pg_ctl em diretório temporário, destruído ao final).
**Nenhuma migration foi aplicada em banco operacional existente.**

## 5. Conectividade entre agentes

`src/server/protocolo.ts` define o **protocolo interno padronizado** (envelope) com:
identificador de missão, objetivo, contexto, restrições, critérios de aceite, dependências,
agente responsável, estado da execução, resultado, evidências, consumo e erros.

Adaptadores evoluídos para: **ChatGPT, Codex, ChatGPT Work, TRAE, Manus, FIRE Private AI e
agentes personalizados**. O `POST /agentes/envelope` é o **gateway extensível** para
integrações futuras. Sem integração oficial disponível, o agente permanece em **fluxo manual
assistido** — nenhuma API privada é inventada nem interface automatizada sem autorização.

## 6. Orquestração persistente

`src/server/orquestracaoPersistente.ts` evoluí o motor (determinístico) com: **fila
persistente**, **recuperação após reinicialização**, **locks/leases**, **idempotência
server-side** (`chaveIdempotencia`), **heartbeat**, **controle de concorrência**,
**cancelamento**, **timeout**, **retentativas com backoff exponencial** e **recuperação de
execuções interrompidas**.

Garante que uma missão **não seja executada duas vezes indevidamente**. Temporizadores do
navegador **não** são confundidos com execução persistente em servidor — o estado de
execução vive no backend.

## 7. Protocolo interno (envelope)

Campos do envelope (resumo):

```json
{
  "missaoId": "uuid",
  "objetivo": "string",
  "contexto": "string",
  "restricoes": ["..."],
  "criteriosAceite": ["..."],
  "dependencias": ["uuid"],
  "agenteResponsavel": "id",
  "estado": "pendente|executando|concluida|falha|cancelada",
  "resultado": {},
  "evidencias": [],
  "consumo": { "tokens": null, "custo": null },
  "erros": []
}
```

`consumo` é sempre **informado** pelo operador; nenhuma API paga é consultada.

### 8.1 Estados explícitos
